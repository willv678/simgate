\begin{abstract}
\guide{About 150 words, written last, with the final numbers. Four sentences: (1) the problem: stress testing an end-to-end driving policy in closed loop takes thousands of runs; by hand it is slow, and left unattended it fails silently; (2) what SimGate is: an AI agent that runs the whole campaign, choosing only from fixed menus that code checks and scripts carry out; (3) the evidence: the scale of the unattended campaign, the share of failed launches healed with no person, and that no planted invalid run was kept; (4) the main finding: where failures are rare, letting the agent choose the next tests confirms the hardest cases sooner than rules, random search or Optuna.}
Stress testing an end-to-end driving policy in simulation is still a loop that people run by hand. They turn a goal such as ``find when the policy crashes as another car cuts in'' into concrete tests, run them, check the results and choose the next tests. Every step needs attention, since a run can finish normally even though its setting never took effect or its results were lost, and a campaign takes thousands of runs. SimGate automates the whole loop from a plain-English brief. An AI agent plans the study, chooses each round of tests, handles simulations that fail and explains each crash, but it only picks from fixed menus. Plain code checks every choice and every run, and scripts carry out what passes. Testing an end-to-end driving policy on recorded real-world scenes, SimGate ran a three-week campaign with no person relaunching or checking runs, and 99.0\% of its 10,920 runs ended as usable data. Runs broken on purpose would have put 294 invalid results in the data; the checks let none through. Where failures are rare, the agent found 33 of 35 hardest cases in seven attempts, against at most 13 for rule-based search, random search and Bayesian optimization.
\end{abstract}

\section{Introduction}\label{sec:intro}
\guide{\textbf{Paragraph 1: background and gap.} Motivate accelerated stress testing of end-to-end driving policies~\cite{feng2021nade,feng2023d2rl}, now possible in closed loop on real recorded scenes with neural-reconstruction simulators~\cite{ljungbergh2024neuroncap,zhou2024hugsim,alpasim}. State the gap: a campaign is thousands of runs that someone must choose, relaunch when they crash, and verify; left unattended it fails silently (use concrete early examples: a misconfigured model, a delay that never applied, missing results), and simulation results can themselves be flaky or nondeterministic ~\cite{osikowicz2025flaky,amini2024flaky,chance2022determinism}. Then the second half of the gap: handing the campaign to an AI agent that acts in a fully closed loop does not fix this by itself. An evaluation of an AI-scientist system found many experiments failing and hallucinated numbers in its papers~\cite{beel2025sakana}; such systems hide pitfalls that only full trace logs reveal~\cite{luo2025pitfalls}; coding agents make checks pass by deleting failing tests~\cite{zhong2025impossiblebench}; data-analysis agents finish without error yet answer the wrong question~\cite{yan2026failloudly}. Checking has not kept pace with what agents produce~\cite{mo2026trustworthy}.}

Accelerated stress testing finds where a driving policy fails by steering simulation toward rare, critical events~\cite{feng2021nade}. Neural-reconstruction simulators now make this possible in closed loop on real recorded scenes, with an end-to-end policy driving from camera images~\cite{ljungbergh2024neuroncap,alpasim}. In practice it is still a loop run by hand. A person starts from a simple goal, such as finding where the policy crashes when a car cuts in, and must turn it into concrete tests, run them, check the results and choose the next tests, over thousands of runs. Every step needs attention, because a run can look finished and still be wrong, for example when a requested setting never took effect or its results were never saved. Handing the loop to an AI agent does not fix this by itself. An evaluation of an AI-scientist system found 42\% of its experiments failing from coding errors and hallucinated numbers in some of its papers~\cite{beel2025sakana}, and data-analysis agents can finish without error yet answer the wrong question~\cite{yan2026failloudly}.


\guide{\textbf{Paragraph 2: approach and core contributions.} Open with the approach: hand the whole campaign to an AI agent but never let it decide what counts: it only proposes from fixed menus, code checks every proposal and every run, and every failure is kept with its evidence. Then list the contributions, each naming where it is described and where it is validated. (1) An agent that runs stress testing of an end-to-end driving policy end to end and unattended, in a neural-reconstruction simulator (Sec.~\ref{sec:method}; Sec.~\ref{sec:healing}). (2) An action design that makes it trustworthy: every job is a contract with a fixed menu, checked by code and carried out by scripts; the recovery menu is checked exhaustively, and every kept run is verified against its request (Sec.~\ref{sec:overview}, \ref{sec:gate}, \ref{sec:diagnose}; Sec.~\ref{sec:validity}). (3) Evidence that letting the agent choose the next tests confirms the hardest cases sooner where failures are rare, at an equal budget against rules, random search and Optuna (Sec.~\ref{sec:outer}; Sec.~\ref{sec:discovery}). (4) Results a person can check: every failure the agent handled with its evidence, a case card for every confirmed hardest case, and the agent's failure explanations checked against rules and people (Sec.~\ref{sec:healing}, \ref{sec:triage}, \ref{sec:cases}). Do not claim to be the ``first''.}

SimGate automates the whole loop from a plain-English brief, but never lets the agent decide what counts. The agent only proposes, from fixed menus; code checks every proposal and every run, scripts carry out what passes, and every failure is kept with its evidence. The contributions are:
\begin{enumerate}
\item A system that runs the whole stress-testing loop from a plain-English brief, unattended, on an end-to-end driving policy in a neural-reconstruction simulator (Sec.~\ref{sec:method}, \ref{sec:healing}).
\item A design that keeps the agent in check, in which every job it does is a choice from a fixed menu that code checks and a script carries out, and every kept run is checked against what was asked (Sec.~\ref{sec:overview}--\ref{sec:diagnose}, \ref{sec:validity}).
\item Evidence that the agent finds the hardest cases sooner than rules, random search and Optuna when failures are rare, at the same run budget (Sec.~\ref{sec:discovery}).
\item Results a person can check, with the evidence for every handled failure, a case card for every hardest case, and the agent's crash explanations checked against code and people (Sec.~\ref{sec:triage}, \ref{sec:cases}).
\end{enumerate}


\guide{\textbf{Paragraph 3: organization of the paper.} One sentence per section. Sec.~\ref{sec:related} reviews accelerated stress testing, LLMs in scenario generation and testing, and agents that act safely. Sec.~\ref{sec:method} presents the framework around Fig.~\ref{fig:system}: its overview, the outer loop that plans a study and chooses the next runs, the inner loop that checks each run and heals failed ones, and how a study closes with triage and a report. Sec.~\ref{sec:results} describes the simulation setup and validates the framework: the validity of kept runs, self-healing in unattended operation, corner-case discovery across search methods, the reliability of failure triage, and the failures found in the policy under test. Sec.~\ref{sec:conclusion} concludes with limitations and future work.}

\section{Related Work}\label{sec:related}
\guide{Three short paragraphs. (1) Accelerated and adaptive stress testing (NADE~\cite{feng2021nade}, D2RL~\cite{feng2023d2rl}, adaptive stress testing~\cite{lee2020ast,koren2018ast}, Bayesian optimization~\cite{abeysirigoonawardena2019adversarial,osikowicz2026mfbo}): they supply search algorithms; this paper studies who chooses the next test and how a campaign stays valid. (2) LLMs in scenario generation and testing (LLM-attacker~\cite{mei2025llmattacker}, Teach-to-Crash~\cite{ghazal2026teachtocrash}, EvoDrive~\cite{nie2026evodrive}, PlannerForge~\cite{gao2026plannerforge}, LEADE~\cite{tian2024leade}, and the IV precedents Chat2Scenario~\cite{zhao2024chat2scenario}, EC-Detector~\cite{pokharkar2026ecdetector} and ARISE~\cite{poddubnyy2026arise}): one line each on what they do and how SimGate differs. (3) Agents that act safely (Simplex~\cite{sha2001simplex,seto1998simplex,mehmood2022blackbox}, shielding~\cite{alshiekh2018shield}, runtime rules on agent actions~\cite{wang2026agentspec,shieldagent2025}, self-healing pipelines~\cite{selfhealing2026}), and the evidence that agents running experiments or analyses on their own~\cite{lu2024aiscientist,boiko2023coscientist} produce unreliable results~\cite{beel2025sakana,luo2025pitfalls}, with the auditable runtimes proposed against it~\cite{yan2026failloudly}. Close with one sentence on what sets this paper apart.}

Earlier work offers smart ways to search for rare failures in driving policies. Some methods learn where to sample or how to act adversarially~\cite{feng2021nade,feng2023d2rl}, some treat the search as a sequence of decisions~\cite{lee2020ast}, and some use Bayesian optimization~\cite{abeysirigoonawardena2019adversarial}. These are search algorithms. We ask instead who decides what to test next, and how a campaign stays correct when no one is watching. Neural-reconstruction simulators make such testing possible on real recorded scenes~\cite{ljungbergh2024neuroncap,alpasim}.

Most work on LLMs in scenario testing uses an LLM for one step of building a scenario. LLM-attacker~\cite{mei2025llmattacker} has LLM agents choose which vehicles attack, EC-Detector~\cite{pokharkar2026ecdetector} lets an LLM refine scenario parameters from simulation outcomes, and ARISE~\cite{poddubnyy2026arise} has an LLM write and repair scenario scripts until they run. EvoDrive~\cite{nie2026evodrive} goes further, with unattended LLM agents that evolve scenario generators under a deterministic validator, against rule-based and RL egos in MetaDrive and CARLA; PlannerForge~\cite{gao2026plannerforge} lets people test classical planners through a chat interface. In SimGate the agent runs the whole campaign, the search methods are compared at the same budget under the same checks, and the policy under test drives from camera images.

To keep the agent safe, SimGate borrows the Simplex idea~\cite{sha2001simplex}, in which a capable but unverified component proposes and a simple, verified one decides what actually runs.

\section{Framework Architecture and Design}\label{sec:method}
\guide{\textbf{Opening paragraph.} Three or four sentences: SimGate runs a campaign as two nested loops (Fig.~\ref{fig:system}); the agent proposes, code checks and acts. Then what each subsection covers: overview (\ref{sec:overview}), outer loop (\ref{sec:outer}), inner loop (\ref{sec:gate}, \ref{sec:diagnose}), triage and report (\ref{sec:explain}).}

SimGate is two loops, one inside the other (Fig.~\ref{fig:system}). The outer loop decides what to test next. The inner loop runs each simulation, checks that it really happened as asked, and fixes it when it breaks. In both, the agent only suggests; plain code checks every suggestion and every run, and scripts do the work.

\subsection{Framework Overview}\label{sec:overview}
\guide{Present Fig.~\ref{fig:system} as a whole: a brief comes in, a checked plan sets up a study, the outer loop picks each round of runs, the inner loop runs, checks and heals every run, kept outcomes go back to the goal check, and once the goal is met each failure is explained and a report answers the brief. Explain the colors: orange boxes are the agent, which only proposes; blue boxes are plain code, which checks every proposal and acts on it; grey is a person (who writes the brief, approves the plan, enacts a new rule and takes over a halted run). Define a campaign and a study (scenes, knobs, goal, budget). Then the design rule shared by every orange box: a contract with five parts (when code calls it, what it sees, what it may answer from a fixed menu or schema, who checks the answer, and who acts: a script, never the agent). Leave the concrete simulator and scenarios to Sec.~\ref{sec:setup}.}

A study answers one question about the policy, written as a plain-English brief. One brief asks which mixes of a car's timing, its speed and the ego's speed make the policy crash or leave the road when that car cuts in or brakes ahead. The study fixes the recorded scenes to use, the knobs it may turn and their legal values, a run budget split into rounds, and a goal.

Every job the agent does (orange in Fig.~\ref{fig:system}) is a contract, run as one fresh model call with no memory of earlier calls. The contract says when code calls the agent, what it sees (named inputs and, for some jobs, read-only tools), what it may answer (a fixed menu or JSON schema), which code checks the answer, and which script acts on it. Seven contracts cover everything from planning a study to writing the report.

\subsection{Outer Loop: Planning and Choosing the Next Runs}\label{sec:outer}
\guide{The top band of Fig.~\ref{fig:system}, left to right. The planner turns the brief into scenes, knobs, rounds and a goal, and code checks the plan before a person approves it. The proposer (rules, a baseline, or the agent) picks each round; every proposed run is checked before it is queued (a candidate scene, legal knob values) and anything else is dropped. Kept outcomes return to the goal check: define a confirmed hardest case precisely (a setting whose failure rate is surely above one half, by a confidence interval over its repeats, at most one per scene), since Sec.~\ref{sec:results} counts them. List the search methods that can act as the proposer (rules, random search with repeats, Optuna~\cite{akiba2019optuna} with repeats, and the agent alone or combined with either), all under the same gate and budget.}

The planner turns the brief into scenes, knob ranges, rounds and a goal. Code checks that every scene and knob exists and that the budget stays under a cap, and a person approves the plan. Each round, a proposer picks ten runs; any run outside the plan or with an illegal knob value is dropped.

Every study asks for the $k=5$ hardest cases, at most one per scene, so a method cannot find one bad scene and count it five times. A setting counts as a \emph{confirmed hardest case} only once reruns show it fails more often than not, meaning the 90\% Wilson interval of its failure rate lies entirely above one half. That takes at least three failures in three runs. A study stops when the goal is met or the budget runs out.

The proposer is the only part that changes between methods. The \emph{rules} start at the middle of each knob's range, repeat the setting that came closest to failing and step each knob one notch from it. \emph{Random search} and \emph{Optuna}~\cite{akiba2019optuna}, a widely used hyperparameter-optimization library whose default sampler is Bayesian, run \emph{with repeats}, so up to half of each round reruns near failures; a search that never repeats a setting can never confirm one. The \emph{agent} chooses freely, and two hybrids restrict it to the candidates of the rules or of Optuna. Each round the agent sees every kept run, a per-setting summary with failure-rate intervals and how close the goal is. Its second version, the one evaluated in Sec.~\ref{sec:discovery}, also sees triage's explanation of each failure (Sec.~\ref{sec:explain}), facts about each scene and a note it wrote itself the round before. Its instructions were revised once, on the 10\,Hz studies, and frozen before the two main studies ran.

\subsection{Inner Loop: Running and Checking Each Run}\label{sec:gate}
\guide{The upper row of the bottom band of Fig.~\ref{fig:system}. Each run passes checks before launch, runs in closed loop, and passes checks after it, in a fixed order; it is kept only if the requested scenario provably happened (read back from its logs) and its motion is physically plausible. Stress that code, not the model, decides that a run failed and names the reason. Define the outcome a kept run carries: a failure counts only if the policy is at fault after it takes over. Then the batch audit and how new checks are learned: the auditor flags runs that are wrong in the same way and proposes rules; code admits a rule only if it catches the flagged runs and fires on no clean run; a person enacts it; from then on it is checked on every run \emph{(Fig.~\ref{fig:system} does not show the auditor yet; add it when the figure is redrawn)}.}

A simulation can finish without error and still be wrong, so every run is checked before and after it runs. Before launch, code rejects a configuration the simulator would not run as asked, and checks that the machine has free GPU memory and disk, no leftover containers and a free network. After the run, code reads the exit code and the results file, confirms that every requested setting reached the simulator and that each knob actually took effect (read back from the run's own log), tests that the motion is physically possible from its acceleration, jerk, yaw rate and speed, and applies every rule added by the batch audit. Code, not the model, decides that a run failed and says why. In a kept run, a crash counts only if it is the policy's fault, meaning the ego leaves the road or a front or side collision begins after the policy takes over.

Some faults look normal one run at a time but stand out in a batch. After each batch, the auditor compares the runs with a reference run of each scene, flags runs that are wrong in the same way and proposes a rule to catch them. Code admits the rule only if it fires on every flagged run and on no clean run; a person switches it on, and from then on it is checked on every run with no model call.

\subsection{Inner Loop: Healing Failed Runs}\label{sec:diagnose}

Fig.~\ref{fig:contract} zooms into that row: the five steps around the investigator, of which only the third is the agent. Fig.~\ref{fig:io} zooms further into steps 2 and 3: what the agent is given and what it may return. Walk through them: the diagnose contract is called only on a failed run and sees the failure status, the config, the attempt count, error lines and a machine snapshot, with read-only tools. It answers one of five skills; for each, say what the recovery script does with it and when the validator accepts it. RE-RUN queues the same run again. CONFIGURE changes how the run executes (context length, scene file, where the traffic model runs), never what it measures. RESTART\_CLEANUP takes down this run's containers, then reruns it. HALT stops the run for a person; it is always accepted, and after a machine failure it stops the whole batch. Every skill but HALT needs an attempt left. Code restricts the choice before launch and through the attempt budget, while after launch every skill is allowed and the choice is the agent's (for example, halting every physically wrong run). Note that the tools are read-only by permission, not by instruction. End with the exhaustive check of every answer the agent could give. \emph{Redraw Fig.~\ref{fig:contract} in the paper's style: title it by its role, the inner loop's investigator, and show only the five steps; campaign counts belong in Sec.~\ref{sec:healing}, not in this figure.}}

Left, the input that code packs as JSON: the failure status, the config, the attempt count and its limit, up to 15 error lines, and the machine snapshot. When a run fails, code asks the agent once what to do. The agent sees why it failed, its configuration, how many attempts are left, up to 15 error lines and a snapshot of the machine, and may look around with read-only tools; the tools are read-only by permission, not just by instruction. It answers with one of five skills. RE-RUN tries the same run again, and RESTART\_CLEANUP first takes down the run's containers. CONFIGURE changes how the run executes (context length, scene file, where the traffic model runs) but never what it measures. CLEANUP\_ENV clears leftovers from the whole machine, at most once per run. HALT stops the run for a person and is always accepted. Every skill but HALT needs an attempt left, and no run launches more than three times.

Because the menu is small, we could test every answer the agent could ever give, running the real validator and recovery script over all 49 failure states and 3,822 transitions. The test checks that no failed run is kept, no recovery loops, and no kept run measures something other than what was asked. It found one real bug, a CONFIGURE that could silently undo the planner delay being tested and still produce a kept run. We removed that option, which is why a fix may change how a run executes but never what it measures.


\subsection{Closing a Study: Triage and Report}\label{sec:explain}
\guide{The right end of the top band of Fig.~\ref{fig:system}. Triage: for each failed run the agent sees frames before the failure and the metrics, and answers a cause from a fixed list and whether the policy was at fault; counts over these answers are computed by code. Report: the agent answers the brief by citing setting ids; code writes every number, and a report with a hand-written count is refused.}

For each crash, the triage contract looks at frames before and at the failure, with the speed and the gap to the nearest road user, and picks a cause from a fixed list (no braking for the car ahead, steered into a road user, left the road, a road user drove into the ego, rendering fault, other) and whether the policy was at fault. Code computes every count over these answers, and an explanation never decides which runs are kept. At the end, the report answers the brief by pointing to specific settings; code writes every number, and a report with a hand-typed count is refused.

\subsection{Simulation Setup}\label{sec:setup}
\guide{Two parts. \textbf{Simulation:} the simulator and policy (AlpaSim~\cite{alpasim}, VaVAM~\cite{bartoccioni2025vavam}, linear MPC tracking, replayed traffic; planning at 2 Hz and 10 Hz), the knobs, the test scenarios (studies mapped to Euro NCAP tests~\cite{euroncap2023vru,euroncap2023c2c}), repeats and run budgets per method, the metrics (confirmed hardest cases, runs to reach the goal, model time) and the statistical tests. \textbf{Computing environment:} one workstation (GPU model and memory, CPU, RAM, disk, operating system) running two simulations at once on its single GPU; the simulator in containers, with the added retiming and seeding hooks off by default; the agent's model and how it is called (one fresh headless call per decision, read-only tools, time per call); run time (simulated seconds and wall-clock per run at each planning rate, total GPU hours). \emph{Confirm the exact hardware and software versions for the whole campaign; a short table is a common way to report them.}}

We test VaVAM~\cite{bartoccioni2025vavam}, an end-to-end policy that plans from camera images, in AlpaSim~\cite{alpasim}, which replays recorded drives as neural reconstructions and closes the loop with the policy; we use the 139k-step pretrained checkpoint of AlpaSim's default VaVAM configuration. A linear MPC follows the policy's plan, and other road users replay their recorded tracks. The ego replays the human's driving for the first 4.5\,s, then the policy takes over (the hand-off). Planning runs at VaVAM's own 2\,Hz or at 10\,Hz with the camera at 2\,Hz. The knobs are when and how fast a recorded road user moves (a time shift of $-2$ to $+2$\,s and a speed scale of $0.5\times$ to $2\times$, applied by a retiming hook we added to AlpaSim), the ego's speed at the hand-off ($0.6\times$ to $1.4\times$ the recording), and a sideways offset of the plan ($-0.5$ to $+0.5$\,m).

Two main studies ran after the agent's instructions were frozen. \emph{Car cut-in and braking} is the hard one. A car cuts in or brakes ahead on 10 scenes where the policy passes as recorded, so failures are rare and have to be found among 2,700 settings of three knobs, with 60 runs at 2\,Hz. In \emph{lane keeping}, the plan is pushed sideways on 12 straight scenes while the ego's speed varies, with 50 runs at 10\,Hz. Three earlier studies ran at 10\,Hz. Two of them, a pedestrian crossing and a car ahead braking, map to the Euro NCAP AEB VRU and car-to-car tests~\cite{euroncap2023vru,euroncap2023c2c}, and the third, a car cutting in, follows the same style. Each method ran each main study from scratch \verify{7} times and each earlier study 3 times.

For each attempt we count the hardest cases confirmed within the budget and the runs needed to reach the goal. We planned three comparisons in advance, the agent against random search, Optuna and the rules on the two main studies, and test them with an exact two-sided permutation test, Holm-corrected over the three; every other comparison is descriptive.

Everything ran on one workstation (NVIDIA RTX 4500 Ada, 24\,GB; Intel Core Ultra 9 285; 62\,GB RAM; Ubuntu 22.04), two simulations at once on its single GPU, with AlpaSim \verify{version} in containers and the added retiming and seeding hooks off by default. The agent is Claude Opus~5.5, called once per decision through the Claude Code command line. A run takes about 3\,min with launch and checks (rollouts of 47\,s at 2\,Hz and 84\,s at 10\,Hz); the campaign used \verify{N} GPU hours.

\subsection{Validity of Kept Runs}\label{sec:validity}
\guide{Test whether every kept run is real data, in both directions: bad runs must be caught and good runs kept. (1) Planted faults: in three campaigns, runs were broken on purpose in ways that still end normally (deleted or corrupted results, a requested setting silently dropped, the recorded human driving the whole run, no controller in the loop). Count the invalid runs kept with no gate, with the per-run gate, and with the batch audit added, and give an upper bound on the share that could still slip through. Say which faults only the batch audit catches and why (they look the same in every run of a batch). (2) False alarms: the physics check on clean runs (none should be thrown away) and on runs with silent motion faults (all should be caught). (3) Close by noting that every later result uses kept runs only. \emph{Add a small table, generated from the data: invalid runs kept per planted-fault campaign with no gate, the per-run gate, and gate + audit. No figure is needed.}}

Here we ask whether bad data ever gets through. To find out, we broke runs on purpose in four campaigns (C1--C4). Each plans 50 runs, five of each of eight fault kinds plus ten clean runs, once per recovery handler of Sec.~\ref{sec:healing}. Five of the kinds are silent, meaning the run ends normally even though something is wrong. Its results were deleted or corrupted, a requested setting was dropped, the recorded human drove the whole run, or no controller was in the loop. C1 ran with the physics bounds off and C2--C4 with them on; in C3 and C4 the silent faults repeat on every retry, as a configuration bug would, and C4 repeats C3 on six scenes no other campaign used.

Without checks, 294 invalid runs would have been kept (Table~\ref{tab:validity}). The per-run checks cut that to 40, all of them runs on rails or without a controller. Thirty were in C1, where nothing looked at the motion, and ten were runs without a controller in C2 and C3 whose motion still looked normal. These look identical across a batch, so only comparing runs against a reference from the same scene exposes them. The batch audit does exactly that, and with it no invalid run was kept, a one-sided 95\% upper bound of 1.0\% on the share that could slip through. We planted these faults ourselves, so this shows the checks catch these kinds of fault, not every possible one. The checks also keep good data, since the physics check raised no false alarm on 256 clean runs.

\subsection{Self-Healing in Unattended Operation}\label{sec:healing}
\guide{Test whether the agent keeps a long campaign running without a person, using every failed launch of the whole campaign. (1) Scale and outcome: runs asked for, runs kept on the first try, launches that failed and went to the agent, and how many of those were healed or stopped for a person (Fig.~\ref{fig:healing}). (2) What the agent chose: for each kind of failure, the skill it picked and how the run ended; every answer passed the validator, and every retry ran exactly the settings asked for. (3) Honest accounting: most heals are out-of-memory crashes answered by a plain rerun, which a retry script would also do; the agent's value is in the rest, such as halting runs that failed the physics check instead of rerunning them and clearing a machine that was not ready. (4) Against a retry script: on the planted-fault campaigns, the same faults handled by a fixed script, by the agent without tools, and by the agent with read-only tools; compare valid runs kept, launches used and runs stopped, and note where the agent without tools fails (results missing despite a normal exit). Report the agent's time per decision. \emph{Regenerate Fig.~\ref{fig:healing} from the final data before submission. Give (4) as a few numbers in the text, or a small table if space allows.}}

Here the question is whether the campaign keeps going with no one watching. From 6 to 28 October it asked for 10,920 runs and made 11,252 launches (Fig.~\ref{fig:healing}). Most runs just worked, with 10,492 kept on the first try. The 467 launches that failed went to the agent, which fixed 342 and stopped 125 for a person; in all, 10,810 runs (99.0\%) ended as usable data. Every answer passed the validator, every retry ran exactly the settings asked for, and the median decision took 8.3\,s. Runs stopped when the disk filled on 22 October were redone and are left out of these counts.

Most fixes are simple. Of the failures, 312 were GPU out-of-memory crashes, answered with RE-RUN 307 times; 104 were runs that failed the physics check, all halted, since rerunning reproduces the fault; 25 were launches onto a GPU still held by the previous run, answered with CLEANUP\_ENV 24 times; and 26 were other crashes. A plain retry script would make most of these reruns too.

The planted faults show what the agent adds over a script (Table~\ref{tab:recovery}). In C3 and C4 the same faults went to a fixed retry script, to the agent without tools and to the agent with read-only tools. The script kept all 35 runs that can end as valid data, but wasted launches (95 and 102) retrying the 15 faults that come back on every retry. The agent without tools used the fewest launches but kept only 25 and 28: it halted runs whose results were lost after a normal exit, which a rerun fixes. With read-only tools, the agent kept all 35 in 72 launches in both campaigns. It was as reliable as the script without wasting launches on faults a retry cannot fix.

\subsection{Corner-Case Discovery Across Search Methods}\label{sec:discovery}
\guide{Test whether letting the agent choose the next tests finds and confirms the hardest cases sooner, at an equal budget under the same gate. (1) The comparison: each method replaces only the proposer; studies, budgets, rounds and goal stay the same; each method runs several repeats. Report confirmed hardest cases at the budget and runs to reach the goal (Fig.~\ref{fig:discovery}, Table~\ref{tab:methods}). (2) Main result first: the three-knob study, where failures are rare, with five repeats and comparisons planned before the extra repeats were run; then lane keeping, a study the second AI version was not built on; then the car scenes and the pedestrian study, where failures are common. (3) The pattern: the agent's lead grows as failures get rarer, and where failures are common it has no edge (say so); Optuna alone does no better than random search with repeats; the agent restricted to the rules' candidates does well only where those candidates are good. Explain it by where each method looked: the rules start in the middle of each knob's range and step locally, random search and Optuna spread runs thin, the agent uses the physics stated in the brief and repeats what fails. (4) Counting decides the ranking: under a naive collision count (contacts begun before the hand-off, rear-ends by replayed traffic) the ranking changes; show it briefly. \emph{Fig.~\ref{fig:discovery} and Table~\ref{tab:methods} are placeholders with the three 10 Hz studies only; add the three-knob study and lane keeping, ordered from rare to common failures. Compute every test statistic with code.}}

This is the main result. We ask whether letting the agent choose the next tests finds the hardest cases faster. Only the proposer changes between methods, and each ran every main study seven times from scratch (Table~\ref{tab:methods}).

Car cut-in and braking is the hard search, since only 66 of the 814 settings any method tried fail reliably. Here the agent confirmed 33 of a possible 35 hardest cases over seven attempts (all five in five attempts, four in the other two). Optuna confirmed 13, random search 10 and the rules none (Fig.~\ref{fig:discovery}, left). Every attempt of the agent beat every attempt of each baseline, an exact two-sided $p=0.0006$ for each planned comparison, the smallest possible with seven attempts each (0.0017 after Holm's correction). On lane keeping, every method but the rules reaches the goal, so speed decides. The agent needed 17--21 runs (median 19), random search 23--40 and Optuna 25--40 (median 30 each), and the rules never got there within 50 (Fig.~\ref{fig:discovery}, right). Again every agent attempt beat every baseline attempt ($p=0.0006$, Holm 0.0017).

Where failures are common, the agent has no edge. On the 10\,Hz car scenes the AI choosing among the rules' candidates led (17 of 30), and on the pedestrian study every method reached the goal (Table~\ref{tab:methods}).

The agent wins because of where it looks. On car cut-in and braking, 28\% of its runs landed on a setting that fails reliably, against 12\% for Optuna, 7\% for random search and none for the rules, and it reached all 7 scenes that have such a setting (random search and Optuna 5, the rules 0). The rules step one notch at a time from the recording, where these scenes pass. Random search and Optuna spread their runs over the whole grid. The agent knows what each knob means, tries what physics suggests, such as a slower car ahead or a faster ego, and repeats what fails. That knowledge is its advantage, since the baselines treat the knobs as numbers while the agent reads the brief as a person would.

\section{Conclusion}\label{sec:conclusion}
\guide{\textbf{Paragraph 1: summary.} Restate the two main claims in a few sentences: an agent can run stress testing of a driving policy end to end, unattended, when each action is a checked choice from a fixed menu; and letting it choose the next tests pays off most where failures are rare. Say where the code and data are released.}

SimGate shows that an AI agent can run the whole stress-testing loop for weeks with no one watching, as long as every action is a checked choice from a fixed menu, and that letting it choose the next tests pays off most where failures are rare. The code, briefs, failure ledger and case cards are released at \texttt{github.com/willv678/simgate}.


\guide{\textbf{Paragraph 2: limitations and future work.} Pair each limitation with the direction that addresses it: one policy under test (test more end-to-end policies); replayed traffic does not react (use reactive traffic); few scenes for some maneuvers (add more scenario types); few repeats per method (run more repeats, and try other models as the agent). Also state the limitations with no direction yet: rendering is less certain far from the recording, and the human check of the scoring is still pending. End with the confirmed hardest cases reused as regression tests.}

The study has clear limits. We tested one policy, with replayed traffic that does not react to the ego, on recorded scenes whose weather, lighting and road geometry cannot change; more policies, reactive traffic and simulators that generate new conditions are the next steps. Each method ran \verify{7} attempts per main study, with one model as the agent. The baselines are simple (random search and Optuna, no adaptive stress-testing method), and we did not test the agent without knowing what its knobs mean. Rendering is less certain far from the recorded path, where some failures happen (they are flagged). Every confirmed hardest case is exported as an OpenSCENARIO~1.4 scenario, so it can be reused as a regression test.
